# Phase 09.1: Code Review-Driven Refactor — Research

**Researched:** 2026-05-19
**Domain:** Pipeline architecture, streaming semantics, type design
**Confidence:** HIGH (source-code analysis, no external dependencies)

## Summary

This research analyzes the current state of the MQL execution pipeline after Phase 9, evaluates the proposed refactoring design from [09-refactoring-design.md](../09-multi-path-api-engine/09-refactoring-design.md), and provides an independent architecture recommendation.

The central question is: **what is the cleanest architecture for a push-based pipeline that produces (node, path) pairs, given that downstream consumers have different grouping needs?**

After reading all relevant source code, the current implementation suffers from a fundamental layering mistake: path grouping is forced into the pipeline terminal (via `NodeAccumulator` and `currentBatch`) when it belongs in the response layer. The proposed design in `09-refactoring-design.md` correctly identifies this problem. However, the proposed solution **retains unnecessary complexity** in how `NodeWithExplainOut` is used as the pipeline's streaming token.

**Primary recommendation:** The pipeline should emit `TraversalItem` (single-path) tokens directly to a new internal `StreamingTerminal` that bridges to `IQueryResponseFiller`. `NodeWithExplainOut` should remain a **response-boundary type only** — never constructed inside the pipeline except at the terminal boundary. `TraversalItem` is essential and should be kept.

## 1. Current State Analysis

### NodeWithExplainOut — Current API

```java
public record NodeWithExplainOut(MObject node, Collection<PathOutput> whyPaths) {
    public NodeWithExplainOut {
        Objects.requireNonNull(node);
        Objects.requireNonNull(whyPaths);
        if (whyPaths.isEmpty()) throw new IllegalArgumentException("whyPaths must not be empty");
        whyPaths = Collections.unmodifiableSet(new LinkedHashSet<>(whyPaths));
    }
}
```

**Consumers of `NodeWithExplainOut`:**

| Consumer | How it uses the type |
|----------|---------------------|
| `IQueryResponse.items()` | Returns `List<NodeWithExplainOut>` — the public result |
| `IASyncExecution.onItem()` | Fires `Consumer<NodeWithExplainOut>` per event |
| `IQueryResponseFiller.pushItem()` | Internal pipeline-to-response bridge |
| `SourceEvaluator` | Creates single-path instances: `new NodeWithExplainOut(el, List.of(trivialPath))` |
| `StepPipelineExecutor.pushItem()` | Receives from SourceEvaluator, extracts first path (BUG) |
| `QuerySearchEngine` | Only calls `.node()` — ignores paths entirely |
| Tests (acceptance) | Most call `.node()` only; `UnionStepExecutionTest` checks `.whyPaths()` |

**Key observation:** At the pipeline _entry point_ (SourceEvaluator → StepPipelineExecutor), `NodeWithExplainOut` always carries exactly one path. The multi-path case only arises at the _response boundary_ after merging.

### TraversalItem — Current API

```java
record TraversalItem(MObject node, PathOutput path) {
    TraversalItem {
        Objects.requireNonNull(node);
        Objects.requireNonNull(path);
    }
}
```

**Used by:**
- `StepPipelineExecutor.buildChain()` — chain type is `Consumer<TraversalItem>`
- `TraverseStepExecutor.wrapTraverse()` — creates new `TraversalItem(target, extendedPath)`
- `RepeatStepExecutor.wrapRepeat()` — BFS frontier is `List<TraversalItem>`
- `StepPipelineExecutor.executeToList()` — for EXISTS sub-queries

**Key observation:** All pipeline step executors (Filter, Traverse, Repeat, Union) work with `Consumer<TraversalItem>`. They never see `NodeWithExplainOut`.

### StepPipelineExecutor — Current Architecture

The pipeline's `buildPipeline()` returns an `IQueryResponseFiller` that:
1. Receives `NodeWithExplainOut` items from `SourceEvaluator`
2. Extracts the first path (BUG: drops others)
3. Creates `TraversalItem` and feeds it into the chain
4. Terminal consumer accumulates into `NodeAccumulator` (per source item batch)
5. On flush, deduplicates and emits `NodeWithExplainOut` to downstream

**Problems (confirming the code review):**
- Step 2: Silent path drop — only `item.whyPaths().iterator().next()` is used
- Steps 4-5: Batching is per-source-item, which is wrong for streaming
- `globalEmitted` marks nodes "emitted" during batch loop, but if `budget.tryAccept()` fails mid-loop, some marked nodes were never actually emitted

## 2. Architecture Analysis — The Three Options

### Option A: Pipeline emits single-path `NodeWithExplainOut` (proposed in refactoring design)

```
SourceEvaluator → pipeline.pushItem(NodeWithExplainOut(node, List.of(path)))
                    ↓ for each source path
                    chainHead.accept(new TraversalItem(node, path))
                    ↓ ... steps ...
                    terminal emits: downstream.pushItem(new NodeWithExplainOut(item.node(), List.of(item.path())))
```

**Pros:**
- Fixes all bugs
- `IQueryResponseFiller.pushItem()` signature stays unchanged
- SyncQueryResponse does the merging

**Cons:**
- **Type lie:** `NodeWithExplainOut` is documented as "all explanation paths" but in the pipeline it always holds exactly one. The `Collection<PathOutput>` is semantically misleading mid-pipeline.
- **Defensive copy overhead:** Every `new NodeWithExplainOut(node, List.of(path))` triggers the compact constructor which copies into `Collections.unmodifiableSet(new LinkedHashSet<>(...))` — that's a HashSet allocation for a single-element collection.
- **API ambiguity for async consumers:** `PreparedAsyncExecution.onItem()` fires multiple single-path `NodeWithExplainOut` for the same node. Consumers must either deduplicate or accept redundancy. This is documented but architecturally awkward.

### Option B: `NodeWithExplainOut` holds exactly ONE `PathOutput` (type-enforced single-path)

```java
public record NodeWithExplainOut(MObject node, PathOutput path) { ... }
```

**Pros:**
- Type-honest everywhere: pipeline token IS what the name says
- No defensive copy overhead
- `PreparedAsyncExecution.onItem()` semantics are clean: one event = one discovery
- `SyncQueryResponse` groups into a separate collection type for the response

**Cons:**
- **Breaking API change**: `IQueryResponse.items()` would need to return something different (e.g., `Map<MObject, List<PathOutput>>` or a new type)
- **Breaks the semantic contract of "Node with ALL explanations"** — the name `NodeWithExplainOut` implies completeness
- **Two types in public API**: one for streaming events, one for grouped results
- Large test migration

### Option C: Keep `NodeWithExplainOut` as-is at API boundary, use `TraversalItem` internally, bridge cleanly (RECOMMENDED)

```
SourceEvaluator → pipeline.pushItem(NodeWithExplainOut(node, List.of(path)))  [always single-path at entry]
                    ↓ extract all paths, create TraversalItem per path
                    chainHead.accept(TraversalItem(node, path))
                    ↓ ... steps ...
                    terminal: downstream.accept(TraversalItem)  [new internal interface]
                    ↓
StreamingTerminal [owns budget + dedup, bridges to IQueryResponseFiller]:
  - Tracks emitted UUIDs for budget
  - Calls downstream.pushItem(new NodeWithExplainOut(item.node(), List.of(item.path())))
```

With response-layer grouping:
- `SyncQueryResponse.pushItem()` merges by node (LinkedHashMap)
- `PreparedAsyncExecution.pushItem()` fires immediately (one event per path-arrival)

**This is essentially Option A with a clearer internal architecture** — the key insight is that `buildPipeline()` should NOT return an `IQueryResponseFiller` but rather should be restructured so the terminal consumer logic is explicit and separate from the pipeline chain.

## 3. Critical Architecture Decision: Should NodeWithExplainOut hold Collection<PathOutput> or single PathOutput?

### Recommendation: **Keep `Collection<PathOutput>`**

**Rationale:**

1. **The name is a contract.** `NodeWithExplainOut` means "a result node with its explanation(s)." At the response boundary (what the user/UI sees), this MUST be multi-path — a node reachable via two different routes should show both paths.

2. **Single-path at pipeline boundary is acceptable.** `List.of(singlePath)` satisfies the non-empty constraint. The type isn't "lying" — it's saying "here is a node with (so far) one known path." The response layer can merge.

3. **API stability matters.** Tests already use `item.whyPaths().hasSize(2)` assertions. The `UnionStepExecutionTest` explicitly validates multi-path merging. Changing to single-path would require a new response-boundary type.

4. **The overhead concern is manageable.** The `LinkedHashSet` allocation for single-element collections is a micro-optimization concern. If it becomes measurable, a factory method `NodeWithExplainOut.ofSingle(node, path)` could bypass the defensive copy. But premature optimization shouldn't drive architecture.

5. **Async semantics are clear with documentation.** `PreparedAsyncExecution` fires per arrival. Document that same-node may appear multiple times. Consumers wanting grouped results should use `syncExec()`.

**Conclusion:** `NodeWithExplainOut` keeps `Collection<PathOutput> whyPaths`. The type serves dual duty: single-path during streaming, multi-path after response-layer merging. This is acceptable because the invariant (`!whyPaths.isEmpty()`) holds in both cases.

## 4. Critical Architecture Decision: Is TraversalItem still needed?

### Recommendation: **Yes, TraversalItem is essential.**

**Rationale:**

1. **Type-enforced single-path guarantee.** Pipeline steps (Filter, Traverse, Repeat) operate on exactly one path at a time. `TraversalItem(node, path)` makes this impossible to violate. If steps received `NodeWithExplainOut`, they'd need to handle the multi-path case (iterate? pick first? error?).

2. **No allocation overhead.** `TraversalItem` is a record — no defensive copy, no set wrapping. The pipeline creates thousands of these during traversal. The overhead of wrapping in `NodeWithExplainOut(node, List.of(path))` at every step boundary would be wasteful.

3. **Semantic clarity.** `TraversalItem` means "I am traversing this path right now." `NodeWithExplainOut` means "here is a result with its explanations." Different concepts, different types.

4. **Encapsulation.** `TraversalItem` is package-private in `internal.executor`. It never leaks to the public API. This is correct — consumers don't need to know about the internal streaming token.

5. **Used by executeToList().** The EXISTS sub-query path (`StepPipelineExecutor.executeToList()`) collects `List<TraversalItem>` directly. Replacing with `NodeWithExplainOut` would be wrong — EXISTS just needs to know if items exist, not package them for output.

**If NodeWithExplainOut held a single PathOutput, would TraversalItem still be needed?**
Even then, yes — because `NodeWithExplainOut` has validation (non-null, non-empty), defensive copies, and is a public API type. You don't want public API record construction in hot inner loops. `TraversalItem` is a zero-overhead internal token.

## 5. Pipeline Architecture: Recommended Design

### The cleanest architecture

```
┌─────────────────────────────────────────────────────────────────────┐
│  QueryEngine.runQuery()                                             │
│                                                                     │
│  1. Build pipeline: chainHead = buildChain(steps, terminal, ...)    │
│  2. SourceEvaluator produces (node, trivialPath) pairs              │
│  3. For each source element:                                        │
│     chainHead.accept(new TraversalItem(node, path))                 │
│  4. Terminal consumer bridges to IQueryResponseFiller                │
└─────────────────────────────────────────────────────────────────────┘

Pipeline chain:  Consumer<TraversalItem> → Consumer<TraversalItem> → ... → terminal

Terminal consumer responsibilities:
  - UUID-based dedup for budget (count unique nodes only)
  - Budget enforcement (tryAccept on first-seen node)
  - Truncation signaling
  - Emit to downstream: pushItem(new NodeWithExplainOut(node, List.of(path)))

Response layer (IQueryResponseFiller implementations):
  - SyncQueryResponse: merge by node → final items() has one entry per unique node
  - PreparedAsyncExecution: fire onItem immediately, one event per (node,path) arrival
```

### Key change from current design: Remove IQueryResponseFiller from buildPipeline return

Currently `buildPipeline()` returns an `IQueryResponseFiller` that wraps the chain. This conflates two responsibilities:
1. Converting source elements into `TraversalItem` (entry)
2. Budget + dedup at the terminal (exit)

**Recommended refactoring:**

```java
// New: buildPipeline returns a Consumer<TraversalItem> (the chain head)
// Terminal is built internally with budget and dedup
public static Consumer<TraversalItem> buildPipeline(
        List<ResolvedStep> steps,
        ICoreSession session,
        IQueryResponseFiller downstream,
        FrozenLimitsSpec limits) {
    ExecutionBudget budget = new ExecutionBudget(...);
    Set<String> emittedNodeUuids = new HashSet<>();
    boolean[] truncationFired = { false };

    Consumer<TraversalItem> terminal = item -> {
        if (downstream.isComplete()) return;
        String uuid = item.node().getUuid();
        boolean isNewNode = emittedNodeUuids.add(uuid);
        if (isNewNode && !budget.tryAccept()) {
            if (!truncationFired[0]) { ... }
            return;
        }
        downstream.pushItem(new NodeWithExplainOut(item.node(), List.of(item.path())));
    };

    return buildChain(steps, terminal, session, limits, new HashSet<>(), downstream);
}
```

Then in `QueryEngine.runQuery()`:

```java
Consumer<TraversalItem> pipeline = StepPipelineExecutor.buildPipeline(
        resolvedQuery.steps(), this.session, responseFiller, resolvedQuery.limits());

SourceEvaluator.evaluate(resolvedQuery.source(), this.session, pipeline);
// No complete() needed — streaming is immediate
responseFiller.getState().complete(QueryCompletionStatus.ENDED);
```

**Wait** — this changes `SourceEvaluator`'s contract. Currently SourceEvaluator calls `pushItem(NodeWithExplainOut)`. If we change buildPipeline to return `Consumer<TraversalItem>`, SourceEvaluator would need to emit `TraversalItem` directly.

**Actually, this IS cleaner:**

```java
// SourceEvaluator produces TraversalItem directly
public static void evaluate(ResolvedSource source, ICoreSession session, Consumer<TraversalItem> pipeline) {
    // for each valid element:
    pipeline.accept(new TraversalItem(element, trivialPath(element)));
}
```

This eliminates the `NodeWithExplainOut` construction at the source layer entirely. Source elements enter the pipeline as `TraversalItem` (single path = trivial path). The only place `NodeWithExplainOut` is constructed is at the terminal consumer boundary.

### However: This changes the public-facing integration

`SourceEvaluator` currently also pushes diagnostics via `IQueryResponseFiller`. If we change its signature to `Consumer<TraversalItem>`, we need a separate diagnostic channel.

**Pragmatic compromise (Option A with the refactoring design's approach is simpler):**

Keep `buildPipeline()` returning `IQueryResponseFiller` so SourceEvaluator can push both items and diagnostics through the same interface. The `pushItem()` override loops over paths and feeds the chain. This is the design in `09-refactoring-design.md` and it is **correct and sufficient**.

## 6. Final Recommended Design

After evaluating all options, the **refactoring design document's proposal is architecturally sound** with minor clarifications:

### Architecture Summary

| Component | Role | Key Change |
|-----------|------|------------|
| `TraversalItem` | Internal single-path pipeline token | No change |
| `NodeWithExplainOut` | Public result type, `Collection<PathOutput>` | No change |
| `StepPipelineExecutor.buildPipeline()` | Returns `IQueryResponseFiller`; `pushItem()` loops all source paths into chain | Remove NodeAccumulator, currentBatch, globalEmitted |
| Terminal consumer | Emits single-path `NodeWithExplainOut` per discovery; budget counts unique nodes | Simplified from batch-flush to immediate-emit |
| `SyncQueryResponse` | Merges by node (LinkedHashMap) | Add merge logic |
| `PreparedAsyncExecution` | Fires immediately, one event per (node,path) | Add Javadoc |
| `IQueryResponseFiller.complete()` | Keep as no-op extension point | Simplify, document |

### Why this is the cleanest

1. **Minimal API surface change** — `NodeWithExplainOut`, `IQueryResponse`, `IASyncExecution` all stay as-is
2. **Clear layer separation** — pipeline deals in `TraversalItem`, response layer deals in `NodeWithExplainOut`
3. **Each component has one job** — pipeline: traversal + budget; SyncQueryResponse: grouping; PreparedAsync: event dispatch
4. **`TraversalItem` guards invariants** — impossible to accidentally pass multi-path into a step
5. **Budget correctness** — only first-seen nodes count; subsequent paths for same node are free
6. **Streaming restored** — no batching, no flush delay

### One refinement to the proposed design

The proposed terminal has a subtle correctness issue:

```java
boolean isNewNode = emittedNodeUuids.add(uuid);
if (isNewNode && !budget.tryAccept()) { ... return; }
downstream.pushItem(...);
```

If `budget.tryAccept()` returns false (budget exhausted), the node UUID has already been added to `emittedNodeUuids` but was never emitted. If the budget becomes un-exhausted somehow (it can't currently, but defensively), this node would be skipped forever.

**Fix:** Remove from set on budget rejection:

```java
boolean isNewNode = emittedNodeUuids.add(uuid);
if (isNewNode && !budget.tryAccept()) {
    emittedNodeUuids.remove(uuid); // rollback
    if (!truncationFired[0]) { ... }
    return;
}
```

However, since `ExecutionBudget.isExhausted()` is monotonic (once true, always true), and `isComplete()` checks `budget.isExhausted()`, no subsequent items will reach the terminal after truncation. So the current design is correct by accident — the rollback is **defensive but not strictly necessary**. Include it anyway for clarity.

## 7. SyncQueryResponse Merging Design

The LinkedHashMap approach from the refactoring design is correct:

```java
private final LinkedHashMap<MObject, NodeWithExplainOut> itemsByNode = new LinkedHashMap<>();

@Override
public void pushItem(NodeWithExplainOut item) {
    this.itemsByNode.merge(item.node(), item, (existing, incoming) -> {
        Set<PathOutput> merged = new LinkedHashSet<>(existing.whyPaths());
        merged.addAll(incoming.whyPaths());
        return new NodeWithExplainOut(existing.node(), merged);
    });
}

@Override
public List<NodeWithExplainOut> items() {
    return List.copyOf(this.itemsByNode.values());
}
```

**Why LinkedHashMap:** Preserves insertion order (first-discovery order). This matches the spec's "deterministic ordering" requirement.

**Why `MObject` as key:** `MObject` identity in production is UUID-based. Since items in the same session with the same UUID are the same object reference, `MObject.equals()` works correctly as map key.

**Caveat:** The existing `NodeWithExplainOut` record's compact constructor does `new LinkedHashSet<>(whyPaths)` — so the merge creates a temporary `LinkedHashSet`, which the `NodeWithExplainOut` constructor then copies again. This is 2x allocation. Acceptable for correctness; optimize later if needed.

## 8. complete() Analysis

### Current state

- `IQueryResponseFiller.complete()` is defined with Javadoc: "Signals that all source items have been pushed. Implementors that accumulate state flush their results here."
- `SyncQueryResponse.complete()` — empty body, comment says "no accumulation"
- `PreparedAsyncExecution`'s anonymous filler — empty body
- `NOOP_DIAGNOSTIC_SINK` — empty body
- `StepPipelineExecutor`'s returned filler — empty body ("Items are streamed per-source-item")
- Called in `QueryEngine.runQuery()`: `pipeline.complete();`

### After refactoring

With no batching anywhere, `complete()` is a no-op in all current implementations.

### Recommendation: **Keep `complete()` but simplify**

1. **Keep the method on `IQueryResponseFiller`** — it's a useful lifecycle hook for future implementations (e.g., a deduplicating response wrapper, a buffered async dispatch)
2. **Keep the call in `QueryEngine.runQuery()`** — it signals "source evaluation is done"
3. **Simplify all implementations to empty bodies**
4. **Update Javadoc** to say: "Lifecycle hook signaling source evaluation completion. Current implementations are no-ops. Future implementations may use this for final cleanup."

Removing the method entirely would be a gratuitous breaking change to an internal interface that has 4 implementations. The cost of keeping it (one empty method) is negligible.

## 9. Common Pitfalls

### Pitfall 1: Budget applied to paths instead of nodes

**What goes wrong:** If budget counts every `pushItem()` call (one per path), a node reachable via 5 paths costs 5 budget slots, artificially reducing the result set.

**Prevention:** Budget tracks unique node UUIDs. Only the first path for a new node triggers `tryAccept()`. Subsequent paths for the same node are "free."

### Pitfall 2: Path dedup not happening

**What goes wrong:** Same `PathOutput` emitted twice for the same node (e.g., two source elements lead to the same path). `SyncQueryResponse` would have duplicates.

**Prevention:** `PathOutput.equals()` is UUID-sequence-based. `LinkedHashSet` in `NodeWithExplainOut`'s constructor deduplicates. And `SyncQueryResponse` uses `LinkedHashSet` during merge.

### Pitfall 3: emittedNodeUuids vs globalVisited confusion

**What goes wrong:** `emittedNodeUuids` (in terminal) prevents duplicate emission downstream. `globalVisited` (in RepeatStepExecutor) prevents revisiting during BFS. These are different concerns.

**Prevention:** Keep them separate. `emittedNodeUuids` is in the terminal consumer. `globalVisited` is passed to RepeatStepExecutor only. Never conflate them.

### Pitfall 4: Async handler ordering assumptions

**What goes wrong:** Consumer of `PreparedAsyncExecution.onItem()` assumes one call per unique node. After refactoring, same node may appear multiple times.

**Prevention:** Document in `IASyncExecution.onItem()` Javadoc. Tests should verify multi-call for same node is valid.

## Open Questions

1. **Should `SyncQueryResponse` be made thread-safe?** Currently single-threaded. If async execution ever moves to a thread pool, the LinkedHashMap would need synchronization. For now: no. Document single-threaded assumption.

2. **Should `NodeWithExplainOut` compact constructor optimize for single-path?** A `List.of(path)` is already unmodifiable and correctly sized. The constructor's `new LinkedHashSet<>(whyPaths)` + `Collections.unmodifiableSet()` is overkill for a single element. Consider: if `whyPaths.size() == 1`, skip the copy. Defer to implementation phase — measure first.
