## Why This Phase Was Inserted

Phase 09 implementation was completed and all tests passed. However, a code review (ordered post-implementation) identified **four critical issues** in `StepPipelineExecutor` that must be resolved before proceeding to Phase 10 test integration.

### The Four Issues

#### 🔴 CRITICAL — Issue #1: Silent Path Drop

**File:** `StepPipelineExecutor.java::pushItem()`, lines ~155-160

```java
PathOutput singlePath = item.whyPaths().iterator().next();
chainHead.accept(new TraversalItem(item.node(), singlePath));
```

**Problem:** Only the first path from `item.whyPaths()` is extracted; all others are silently discarded.

**Why it matters:** The multi-path feature (the value-add of this milestone) is silently broken at the API boundary. While current sources (`ProvidedSource`, `AllSource`) produce single-path items, `buildPipeline()` is public and the invariant is unenforced.

**Current risk:** Low in practice now; high latent risk for future callers.

---

#### 🔴 CRITICAL — Issue #2: Dedup Pollution

**File:** `StepPipelineExecutor.java::pushItem()`, batch flush loop lines ~165-180

```java
for (NodeAccumulator acc : currentBatch.values()) {
    if (!globalEmittedUuids.add(acc.node().getUuid())) {  // ← UUID registered HERE
        continue;
    }
    if (downstream.isComplete()) { break; }  // ← NOT emitted, but UUID marked
    if (!budget.tryAccept()) { ... break; }  // ← same
    downstream.pushItem(...);                // ← actual emission
}
```

**Problem:** The UUID is marked as "emitted" **before** all guards pass. If `isComplete()` or `budget.tryAccept()` fires, the UUID is marked even though `pushItem()` was never called.

**Why it matters:** Violates the invariant of the dedup set. Currently has no observable effect (once complete, no more items arrive), but is a latent correctness trap.

---

#### 🟡 IMPORTANT — Issue #3: Stale Javadoc

**File:** `StepPipelineExecutor.java::buildPipeline()` Javadoc

```java
* @return an {@link IQueryResponseFiller} whose {@code pushTraversalItem} feeds the chain head
```

**Problem:** `pushTraversalItem` does not exist; the method is `pushItem`.

**Why it matters:** Copy-edit leftover from migration. Causes confusion for maintainers and violates documentation accuracy.

---

#### 🔴 CRITICAL — Issue #4: Architecture Mismatch

**File:** `StepPipelineExecutor.java` — overall design

**Problem:** The pipeline performs **batching and grouping** of paths before emission, accumulating all paths for a node in a `NodeAccumulator` before flushing to downstream. This complexity was added because `NodeWithExplainOut` was changed to hold `Collection<PathOutput>`.

**Why it matters:** Batching is the wrong layer:
- `PreparedAsyncExecution` is a pure event bus; it fires handlers immediately
- `SyncQueryResponse` is a pure list append; it doesn't request grouping
- Neither consumer needs or uses grouped results

The batching **delays streaming** and adds 100+ lines of unnecessary complexity.

## Proposed Solution: Layer Correction

### Principle

> The pipeline is a **pure stream of (node, path) pairs**. Grouping and deduplication belong in the **response layer**, not the pipeline.

### Target Data Flow

```
Source generator
  │  pushItem(NodeWithExplainOut(node, singlePath))
  ▼
StepPipelineExecutor  [clean pipeline: budget + node-UUID dedup only]
  │  NO batching, NO NodeAccumulator
  │  terminal: downstream.pushItem(new NodeWithExplainOut(item.node(), List.of(item.path())))
  │  one item per (node, path) pair discovered
  ▼
IQueryResponseFiller implementation
  │
  ├── PreparedAsyncExecution  →  fire handler immediately, one event per (node, path)
  │                              same node may appear multiple times with different paths
  │
  └── SyncQueryResponse  →  merge by node into LinkedHashMap<MObject, NodeWithExplainOut>
                             items() returns one entry per unique node with all its paths
```

---

## Scope of Phase 09.1

### Changes Required

1. **Remove from `StepPipelineExecutor`:**
   - Delete `NodeAccumulator` inner class
   - Remove `currentBatch: LinkedHashMap<String, NodeAccumulator>`
   - Remove 3-step clear/run/flush cycle in `pushItem()`
   - Remove `globalEmitted: Set<MObject>` cross-batch dedup set

2. **Fix multi-path source handling:**
   - Iterate all source paths (not just first)
   - Fix Issue #1

3. **Simplify terminal consumer:**
   - Emit one `NodeWithExplainOut` per (node, path) pair
   - Budget tracks unique nodes (UUID-based dedup)
   - Fix Issue #2

4. **Update `SyncQueryResponse`:**
   - Add `Map<MObject, NodeWithExplainOut>` accumulator in constructor
   - Merge duplicate nodes into single entry with all paths
   - Expose via `items()` as deduplicated collection

5. **Update `PreparedAsyncExecution`:**
   - No changes to event firing logic
   - Update Javadoc: document that same node may appear multiple times

6. **Fix Javadoc:**
   - Correct method references
   - Update class-level description
   - Fix Issues #3 and #4

### What Does NOT Change

- `NodeWithExplainOut` API (still has `whyPaths: Collection<PathOutput>`)
- `IQueryResponseFiller` contract
- Step execution model (Filter, Traverse, Union, Repeat)
- Budget enforcement
- Test public APIs (tests still pass)

### Expected Outcome

- All four issues resolved
- Pipeline simplified by ~100 lines
- Streaming contract restored
- All tests pass (behavior change is internal only)
