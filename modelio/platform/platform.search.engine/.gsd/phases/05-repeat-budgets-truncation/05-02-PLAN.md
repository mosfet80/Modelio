    **1. Create `ExecutionBudget` class** in `internal.executor` package:

    ```java
    package org.modelio.platform.query.internal.executor;

    /**
     * Tracks execution budgets (item limit and wall-clock timeout) and signals truncation
     * when any budget is exhausted.
     * <p>
     * Thread-safety: NOT thread-safe. Designed for single-threaded push pipeline usage.
     */
    public final class ExecutionBudget {
        private static final int DEFAULT_LIMIT = 1000;
        private static final int DEFAULT_TIMEOUT_MS = 60_000;

        private final int limit;
        private final long timeoutNanos;
        private final long startNanos;
        private int itemCount;
        private boolean exhausted;
        private String exhaustionCause;  // human-readable message for diagnostic

        public ExecutionBudget(Integer limit, Integer timeoutMs) {
            this.limit = (limit != null) ? limit : DEFAULT_LIMIT;
            int effectiveTimeoutMs = (timeoutMs != null) ? timeoutMs : DEFAULT_TIMEOUT_MS;
            this.timeoutNanos = effectiveTimeoutMs * 1_000_000L;
            this.startNanos = System.nanoTime();
            this.itemCount = 0;
            this.exhausted = false;
            this.exhaustionCause = null;
        }

        /**
         * Attempts to accept one more item within the budget.
         * Returns true if the item is within budget and should be processed.
         * Returns false if the budget is already exhausted — caller should stop.
         *
         * On first exhaustion, sets the exhaustion cause message.
         */
        public boolean tryAccept() {
            if (this.exhausted) {
                return false;
            }
            // Check timeout
            long elapsed = System.nanoTime() - this.startNanos;
            if (elapsed >= this.timeoutNanos) {
                this.exhausted = true;
                long elapsedMs = elapsed / 1_000_000L;
                int configuredMs = (int)(this.timeoutNanos / 1_000_000L);
                this.exhaustionCause = String.format(
                    "Execution truncated: timeout (%dms) exceeded after %dms",
                    configuredMs, elapsedMs);
                return false;
            }
            // Check limit
            this.itemCount++;
            if (this.itemCount > this.limit) {
                this.exhausted = true;
                this.exhaustionCause = String.format(
                    "Execution truncated: result limit (%d) reached", this.limit);
                return false;
            }
            return true;
        }

        public boolean isExhausted() { return this.exhausted; }
        public String getExhaustionCause() { return this.exhaustionCause; }
    }
    ```

    Notes:
    - `tryAccept()` checks timeout first (first-hit-wins: whichever fires first).
    - Item count check uses `> limit` because we increment before comparing — item at exactly
      `limit` is the last accepted item.
    - The class is not thread-safe — this is fine since the push pipeline is single-threaded.

    **2. Integrate budget into the terminal consumer and the pipeline wrapper in `buildPipeline`:**

    In `StepPipelineExecutor.buildPipeline`, create the budget from `limits` and wire it in two places:

    ```java
    ExecutionBudget budget = new ExecutionBudget(limits.limit(), limits.timeoutMs());
    ```

    **Terminal consumer** — checks budget after dedup, fires truncation once:

    ```java
    Consumer<NodeWithExplainOut> terminal = item -> {
        if (seen.add(item.node().getUuid())) {
            if (!budget.tryAccept()) {
                // Budget just exhausted — signal truncation once, then stop
                downstream.setTruncated();
                downstream.pushDiagnostic(Diagnostics.info(
                    DiagnosticCode.EXECUTION_TRUNCATED,
                    budget.getExhaustionCause()));
                return;
            }
            downstream.pushItem(item);
        }
    };
    ```

    **Wrapper `IQueryResponseFiller`** — override `isComplete()` and `pushItem()` to short-circuit
    once the budget is exhausted:

    ```java
    return new IQueryResponseFiller() {
        @Override
        public void pushItem(NodeWithExplainOut item) {
            if (!isComplete()) {
                chainHead.accept(item);
            }
        }

        @Override
        public boolean isComplete() {
            // Budget exhaustion acts as a stop signal, just like external cancellation.
            // SourceEvaluator checks isComplete() between items and stops immediately
            // when this returns true — so once the budget fires, source iteration stops.
            return budget.isExhausted() || downstream.isComplete();
        }

        @Override
        public void pushDiagnostic(Diagnostic diagnostic) {
            downstream.pushDiagnostic(diagnostic);
        }

        @Override
        public void setTruncated() {
            downstream.setTruncated();
        }

        @Override
        public CompletableFuture<QueryCompletionStatus> getState() {
            return downstream.getState();
        }
    };
    ```

    Key design points:
    - The budget `tryAccept()` is called AFTER dedup (after `seen.add` succeeds) — this means
      the limit counts unique items pushed to the response, matching the CONTEXT decision:
      "limit counted at response filler (post-dedup)".
    - When budget fires, we call `setTruncated()` + push exactly ONE `EXECUTION_TRUNCATED`
      INFO diagnostic.
    - Overriding `isComplete()` to include `budget.isExhausted()` is the critical stop signal:
      `SourceEvaluator` checks `context.isComplete()` between every source item and exits the
      loop as soon as it returns `true`. Without this override, `isComplete()` would remain
      `false` (the state `CompletableFuture` is only completed after the loop finishes), so the
      source would keep iterating through the entire model after the budget was already hit.
    - The wrapper `pushItem()` short-circuits for defense-in-depth (no chain work when done).

    **3. Also add a periodic timeout check in the pipeline:**
    The timeout check inside `tryAccept()` only fires when an item reaches the terminal consumer.
    For long-running intermediate steps (e.g., a traverse step producing millions of results that
    a filter drops), the timeout might not fire until an item passes all the way through.
    This is acceptable for v1 — the CONTEXT says "periodic nanoTime check" and the terminal
    consumer IS the periodic check point. A more aggressive approach (checking in each step wrapper)
    can be added later if needed.
