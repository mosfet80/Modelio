    Implement the `wrapRepeat` private method in `StepPipelineExecutor`. This is the core
    recursive traversal logic.

    **Method signature:**
    ```java
    private static Consumer<NodeWithExplainOut> wrapRepeat(
            RepeatStep repeat,
            Consumer<NodeWithExplainOut> downstream,
            ICoreSession session,
            FrozenLimitsSpec limits,
            Set<String> globalVisited)
    ```

    **maxDepth validation (done once at wrap time, not per item):**
    - Extract `maxDepth` from `limits.maxDepth()`. If null → unlimited.
    - If `maxDepth != null && maxDepth < 1` → return a consumer that swallows items but pushes
      an ERROR diagnostic via the pipeline (use the downstream's wrapping IQueryResponseFiller
      or capture it). Actually, since `wrapRepeat` only returns a `Consumer`, push the diagnostic
      into the pipeline at build time. The simplest approach: log the error and return a swallowing
      consumer. The resolver could also validate this, but for defense-in-depth, handle it here too.
      **Alternative**: validate in buildPipeline before calling wrapRepeat, and push the diagnostic
      through the downstream filler. This is cleaner — do this.
    - If `maxDepth == 1` → push a WARNING diagnostic with message
      "Repeat step maxDepth=1 is suspicious — repeat body will execute at most once".

    **DFS-push algorithm:**
    For each input item received by the consumer:
    1. The source node is NOT emitted downstream (source exclusion).
    2. Add source node UUID to the global visited set (so it won't be followed again).
    3. Start DFS recursion at depth=1:
       - Build a sub-chain from the RepeatStep's body steps (using `buildChain` with the session).
         Pre-build this sub-chain ONCE when constructing the consumer (not per item).
       - Actually, the sub-chain output goes to a *collector* consumer that collects newly discovered
         nodes for the current depth level.
       - For each depth level (starting at 1):
         a. Execute the body sub-chain on the current frontier (initially just the source node).
         b. The sub-chain pushes results into a collector list.
         c. For each collected result node:
            - If node UUID is already in `globalVisited` → skip it (already discovered).
            - If node UUID is already on the current DFS path stack → cycle detected:
              - Skip the node (don't recurse further).
              - Push WARNING diagnostic with `CYCLE_DETECTED` code, message
                "Cycle detected at node: <nodeName> [<nodeUuid>]", elements = [closingNode].
              - Deduplicate: maintain a `Set<String> cycleReported` to avoid duplicate diagnostics
                for the same closing node UUID.
            - Otherwise: add to `globalVisited`, and if `emitAllDepths` is true, push downstream.
              Add to the next frontier.
         d. If no new nodes were added to the next frontier → stop (BFS-level exhaustion).
         e. If depth == `maxDepth` → stop. If `emitAllDepths` is false, emit the current frontier
            nodes downstream (these are the "deepest reached" nodes).
         f. Increment depth and continue with the next frontier.

    **IMPORTANT design clarification on DFS vs BFS:**
    The CONTEXT says "Streaming DFS-push" but also says the algorithm is flexible as long as
    behavioral decisions are honored. The description above uses a **level-by-level BFS approach**
    which is simpler to implement with maxDepth tracking and emitAllDepths semantics:
    - Level 1: run body on source → collect discovered nodes
    - Level 2: run body on level-1 nodes → collect new nodes
    - Continue until no new nodes or maxDepth hit

    This is equivalent to DFS-push in terms of results (same nodes discovered, same cycle detection),
    but easier to reason about depth. The CONTEXT explicitly allows this flexibility.

    **Path construction:**
    Each node discovered by the body sub-chain already has its path extended by the traverse/filter
    steps in the body. The path accumulates naturally as items flow through the body chain.
    When a node is re-fed as input for the next depth, its path is the path that led to it.

    **Cycle detection detail:**
    The path-stack (ancestors of current recursion) is approximated by the per-invocation frontier
    tracking. In BFS-level execution, a cycle is detected when a body output references a node
    on the current path (any ancestor). Since we track the full `globalVisited` set plus each
    item's `PathOutput.nodes()`, we can check if the discovered node is already in the current
    item's path. Simpler approach: just use `globalVisited` as the dedup mechanism. If a discovered
    node UUID is already in `globalVisited`, it may be a cycle or just a convergence. Either way,
    skip it and if the node is an ancestor in the current item's path, emit the cycle diagnostic.

    Simplified approach for v1: check if the discovered node's UUID equals ANY node in the
    incoming item's `why.nodes()` path. If yes → cycle detected, emit diagnostic.

    **Implementation sketch:**
    ```java
    private static Consumer<NodeWithExplainOut> wrapRepeat(
            RepeatStep repeat, Consumer<NodeWithExplainOut> downstream,
            ICoreSession session, FrozenLimitsSpec limits,
            Set<String> globalVisited) {

        Integer maxDepth = limits.maxDepth();
        boolean emitAllDepths = repeat.emitAllDepths();
        // Pre-build the body sub-chain once
        // Body output feeds into a collector

        return inputItem -> {
            String sourceUuid = inputItem.node().getUuid();
            globalVisited.add(sourceUuid);  // source is visited but NOT emitted

            List<NodeWithExplainOut> currentFrontier = List.of(inputItem);
            Set<String> cycleReported = new HashSet<>();
            int depth = 0;

            while (!currentFrontier.isEmpty()) {
                depth++;
                if (maxDepth != null && depth > maxDepth) break;

                List<NodeWithExplainOut> nextFrontier = new ArrayList<>();
                List<NodeWithExplainOut> bodyOutput = new ArrayList<>();

                // Execute body on each frontier item
                Consumer<NodeWithExplainOut> bodyCollector = bodyOutput::add;
                Consumer<NodeWithExplainOut> bodyChainHead =
                    buildChain(repeat.body(), bodyCollector, session, limits, globalVisited);

                for (NodeWithExplainOut frontierItem : currentFrontier) {
                    bodyChainHead.accept(frontierItem);
                }

                for (NodeWithExplainOut discovered : bodyOutput) {
                    String uuid = discovered.node().getUuid();

                    // Cycle detection: check if node is in current path
                    boolean isCycle = discovered.why().nodes().stream()
                        .anyMatch(n -> n.getUuid().equals(uuid));

                    if (isCycle && cycleReported.add(uuid)) {
                        // Push cycle diagnostic via downstream's filler
                        // (need access to IQueryResponseFiller for diagnostics)
                    }

                    if (!globalVisited.add(uuid)) {
                        continue; // already visited — skip
                    }

                    if (emitAllDepths) {
                        downstream.accept(discovered);
                    }
                    nextFrontier.add(discovered);
                }

                // If not emitting all depths and we're about to stop, emit this frontier
                if (!emitAllDepths && (nextFrontier.isEmpty() || (maxDepth != null && depth >= maxDepth))) {
                    for (NodeWithExplainOut item : nextFrontier) {
                        downstream.accept(item);
                    }
                }

                currentFrontier = nextFrontier;
            }
        };
    }
    ```

    **Diagnostic push mechanism:**
    The `wrapRepeat` needs access to an `IQueryResponseFiller` for `pushDiagnostic`. But the current
    chain is built from `Consumer<NodeWithExplainOut>` only. Options:
    - Thread an `IQueryResponseFiller` reference through the chain (add parameter to wrapStep).
    - Use the `downstream` IQueryResponseFiller from `buildPipeline` which is already captured
      in the lambda scope of the terminal consumer — but it's not directly available to wrapStep.

    **Solution:** Add an `IQueryResponseFiller diagnosticSink` parameter to `buildChain` and `wrapStep`.
    The `buildPipeline` method captures the `downstream` filler and passes it as the diagnostic sink
    to all step wrappers. Steps that need to emit diagnostics (wrapRepeat) use this sink.
    Updated signatures:
    - `buildChain(steps, terminal, session, limits, globalVisited, diagnosticSink)`
    - `wrapStep(step, downstream, session, limits, globalVisited, diagnosticSink)`
