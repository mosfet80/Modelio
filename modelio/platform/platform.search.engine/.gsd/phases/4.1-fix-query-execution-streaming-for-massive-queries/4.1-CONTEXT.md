# Phase 4.1: Fix Query Execution Streaming for Massive Queries — Context

**Gathered:** 2026-02-23
**Status:** Ready for planning

<domain>
## Phase Boundary

Rework the step execution pipeline so results flow incrementally — using a **push model** — from source through every step to the `IQueryResponse` terminal, without any intermediate `List<MObject>` buffering between steps.

This phase does NOT add hard execution limits or budget enforcement (that is Phase 5).
This phase should not change public API contracts (`IASyncExecution`, `prepareAsync`, `syncExec`) beyond what is needed to wire the pipeline, unless it simplifies implementation.

</domain>

<decisions>
## Implementation Decisions

### Streaming scope

- **Push model selected**: each step receives elements one-by-one from upstream and pushes them to a downstream consumer. No pull/reactive library required — a simple `Consumer<MObject>` or equivalent callback chain suffices.
- **End-to-end**: source evaluation (`SourceEvaluator`) must also stream. The `all-instances` source in particular must not materialise a `List<MObject>` before feeding the pipeline.
- **Both sync and async paths** use the same streaming pipeline internally. `syncExec` builds results via the streaming pipeline and materialises only once at the `SyncQueryResponse` boundary.
- **Each step class** owns its own streaming contract: it accepts a downstream consumer and processes elements one-by-one, pushing matching/derived elements forward.
- **Dedup UUID set accumulates in memory**: this is accepted. The dedup set is the only in-pipeline structure allowed to grow proportionally to distinct results seen.
- **Terminal consumer** — Copilot's discretion: choose the cleanest design (e.g. `IQueryResponseFiller.fillResult()` per item, or a dedicated `Consumer<MObject>` fed through the chain).

### Memory boundary contract

- **Only `IQueryResponse` implementation may accumulate** the full result list. The pipeline itself must not hold intermediate collections between steps.
- **Inputs can be large** (tens to hundreds of thousands of `MObject`s for model-wide queries). The pipeline must handle this without an `OutOfMemoryError`.
- **No explicit per-step buffer limit or backpressure** in this phase. Hard limits (`timeoutMs`, `limit`) are Phase 5's responsibility.
- **No snapshot/consistency requirement**: stale reads during traversal are acceptable.

### Copilot's Discretion

- Which concrete abstraction carries the push callback through the pipeline (e.g. `Consumer<MObject>`, a new `IResultSink` interface, or reuse of `IQueryResponseFiller`).
- Whether streaming is introduced in a single refactor or in a plan-per-step-type wave.
- How existing tests are migrated/extended to prove no intermediate buffering occurs (e.g. by streaming a deliberately large fixture).

</decisions>

<specifics>
## Specific Ideas

- The key invariant to test: after the pipeline runs, no `List<MObject>` (other than the `IQueryResponse` internal buffer and the dedup UUID set) should survive on the heap proportional to the total number of intermediate model elements visited.
- A large-model integration fixture (or synthetic `MObject` sequence) may be needed to prove streaming correctness.

</specifics>

<deferred>
## Deferred Ideas

- **Concurrent/interleaved union branches** — streaming union branches in parallel was considered but deferred. Not in this phase.
- **Explicit backpressure / in-flight element cap** — considered but deliberately left to Phase 5 budget enforcement.
- **Snapshot isolation** — consistent model reads during streaming were considered but deferred as out of scope.

</deferred>
