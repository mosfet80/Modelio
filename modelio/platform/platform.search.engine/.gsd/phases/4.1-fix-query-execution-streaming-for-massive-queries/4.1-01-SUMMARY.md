# Phase 4.1, Plan 01: Push-Based Pipeline Summary

**Refactored step pipeline from list-passing to push-based Consumer chain, eliminating intermediate List buffering between steps**

## Performance

- **Duration:** ~8 min
- **Started:** 2026-02-23T15:51:27Z
- **Completed:** 2026-02-23T16:00:00Z
- **Tasks:** 2
- **Files modified:** 3

## Accomplishments

- StepPipelineExecutor rewritten with `buildPipeline()` returning an `IQueryResponseFiller` that wraps a `Consumer<NodeWithExplainOut>` chain
- QueryEngine streams source evaluation directly into the step pipeline — no intermediate `SyncQueryResponse sourceCollector`
- Filter, traverse, and union steps are pure consumer wrappers: receive item, process, push downstream
- Terminal dedup consumer (`LinkedHashSet<String>`) is the only pipeline-internal structure proportional to result count
- All 82 existing tests pass unchanged — refactoring is semantics-preserving

## Files Created/Modified

- `platform.search.engine/src/org/modelio/platform/query/internal/executor/StepPipelineExecutor.java` — Complete rewrite: `buildPipeline()`, `buildChain()`, `wrapStep()`, `wrapFilter()`, `wrapTraverse()`, `wrapUnion()`, `executeToList()`
- `platform.search.engine/src/org/modelio/platform/query/internal/QueryEngine.java` — `runQuery()` streams source into pipeline via `buildPipeline()` instead of buffering into `SyncQueryResponse`
- `platform.search.engine/src/org/modelio/platform/query/internal/executor/ExpressionEvaluator.java` — `evaluateExists()` calls `executeToList()` instead of `executeSteps()`

## Decisions Made

- Push-based `Consumer<NodeWithExplainOut>` chain eliminates all intermediate `List<NodeWithExplainOut>` buffering between steps
- Terminal dedup consumer (`LinkedHashSet<String>` for UUID) is the only pipeline structure growing proportional to distinct results
- `executeToList()` is the only list-collecting method, used exclusively for EXISTS sub-queries (single-element scope)
- Union branch head consumers are pre-built once during `wrapUnion()` and reused for every input item
- Invalid/deleted elements in traverse are logged at DEBUG level per-item instead of batch-collected
