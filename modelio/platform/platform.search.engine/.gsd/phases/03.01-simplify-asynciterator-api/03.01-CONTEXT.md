# Phase 3.01: Simplify AsyncIterator API - Context

**Gathered:** 2026-02-19
**Status:** Ready for planning

<domain>
## Phase Boundary

Refactor the internal streaming iteration API used by query execution to make consumption simpler and less error-prone. This phase changes iterator/response contracts and call sites only; it does not add new query capabilities or execution semantics.

</domain>

<decisions>
## Implementation Decisions

### Consumption contract

- Remove `next()` and `hasNext()` from the primary contract.
- Use a single pull method: `nextAsync(): CompletableFuture<Optional<T>>`.
- Keep retrieval single-item only (no native batch API in this phase).
- Add convenience consumption helpers:
  - `forEachRemaining` helper
  - static helper `AsyncIterators.drain(...)`
- Disallow concurrent `nextAsync()` calls on the same iterator and fail fast.
- After terminal completion, subsequent pull calls are considered misuse and fail fast.
- Keep the core interface minimal (no `map/filter/flatMap`, no peek API).
- Provide multiple consumption patterns in docs/examples (manual loop + helper patterns).

### End and error semantics

- `Optional.empty()` is the terminal value for end-of-stream.
- Cancellation is also represented by `Optional.empty()` at pull level.
- Distinguish terminal reasons via response state metadata (`state()`), not via the optional payload.
- Expose state on query response (not iterator), with states: `ACTIVE`, `ENDED`, `CANCELLED`, `FAILED`.
- Name accessor `state()` (not `terminalState()`).
- State transitions are single-path: `ACTIVE` to exactly one terminal state.
- `state()` reads must be thread-safe.
- Producer/runtime failures complete futures exceptionally and also add diagnostics.
- Preserve original exception causes (no forced wrapping).
- Cancellation diagnostics are emitted for external cancellations and use warning severity.
- Reuse existing diagnostic codes (no new diagnostic enum/code additions in this phase).
- If disposal/cancellation happens while a pull is pending, pending pull resolves as empty and final state is `CANCELLED`.

### Disposal behavior

- Keep lifecycle method naming as `dispose()`.
- `dispose()` must be idempotent (repeated calls are no-op).
- `IQueryResponse` owns iterator lifecycle and cascades disposal.
- Keep disposal synchronous in this phase (no `disposeAsync`/`closeAsync`).

### Migration strategy

- Apply a hard break immediately (project is WIP/unpublished).
- Remove old API symbols immediately (no deprecated bridge layer).
- No dedicated migration document is required for this phase.
- Migration completion gate: successful build + targeted iterator/executor tests.

### Copilot's Discretion

- Exact helper method signatures beyond the locked behaviors.
- Exact wording and placement of usage examples across Javadoc/tests.
- Internal synchronization primitives used to enforce fail-fast and state consistency.

</decisions>

<specifics>
## Specific Ideas

- Keep the API intentionally small: one pull entry point plus minimal helpers.
- Distinguish terminal outcomes through response metadata to preserve a simple consumer loop.
- Prefer `state()` naming on response for readability and consistency.

</specifics>
