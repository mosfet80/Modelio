  <action>
    Create `RegressionSuiteTest.java` extending `AbstractMqlTest` in the `engine/acceptance/` package.

    This class builds its own per-test model (via `setUpModel()`) because the regression scenarios
    need specific topologies that differ from the acceptance fixture.

    **Test methods:**

    ### 1. Deduplication

    **`dedup_unionBranches_sameElementAppearExactlyOnce()`**
    - Setup: Package P with class Alpha. Two union branches both traverse OwnedElement, both reach Alpha.
    - Query: `AllSource("Package")` + `UnionStep([branch1=[TraverseStep("OwnedElement")], branch2=[TraverseStep("OwnedElement")]])` + `LimitsSpec()`.
    - Assert: result `containsExactly(alpha)` — exactly one occurrence.
    - This is a regression anchor — existing `UnionStepExecutionTest` covers same behavior but
      in a richer pipeline; this is the minimal isolated form.

    ### 2. Ambiguity → union expansion (end-to-end)

    **`ambiguousEdge_resolvedToUnion_producesResultsAndDiagnostic()`**
    - Setup: two classes C1, C2. A Dependency link from C1→C2. Also set Owner dependency C2.Owner=C1
      so that OwnedElement navigates C1→C2 as well.
    - Use an ambiguous edge token: choose a string that the resolver will match against both an
      MDependency name AND a link metaclass name. The simplest approach: use "OwnedElement" which
      resolves unambiguously to an MDependency. For a true ambiguity test, use "Dependency" which
      could match:
        (a) the MDependency named "Dependency" (if it exists on the source metaclass), or
        (b) the link metaclass "Dependency" (Dependency link objects).
      The resolver should emit AMBIGUOUS_EDGE if both match.
    - Query: `ProvidedSource(List.of(c1))` + `TraverseStep("Dependency")` + `LimitsSpec()`.
    - Assert: result contains `c2`. Diagnostics may contain `AMBIGUOUS_EDGE` if both alternatives matched.
    - **Important**: If the resolver doesn't produce an ambiguity diagnostic for "Dependency" in the
      MofMetamodel environment, this is expected — document in the Javadoc that the test validates
      the traversal result, and ambiguity diagnostic is asserted softly (checked but not required to pass).
      Mark the ambiguity assertion with a descriptive comment.

    ### 3. Truncation — limit-triggered (integration)

    **`truncation_limitTriggered_capsResultsAndDiagnostic()`**
    - Setup: Create 15 classes.
    - Query: `AllSource("Class")` + `LimitsSpec(null, 5, null)`.
    - Assert: `response.items().size() == 5`, `response.isTruncated() == true`.
    - Assert: exactly one `EXECUTION_TRUNCATED` diagnostic.
    - Note: This overlaps with `BudgetExecutionTest.limit_capsResultCount()` — the purpose here
      is a regression anchor in the acceptance package. Keep it concise.

    ### 4. Truncation — timeout-triggered (integration)

    **`truncation_timeoutTriggered_capsResultsAndDiagnostic()`**
    - Setup: Build a deep package hierarchy (root → P1 → P2 → ... → P50, each with 3 classes).
      This creates a model large enough that a 1ms timeout should fire during traversal.
    - Query: `AllSource("Package")` + `RepeatStep(body=[TraverseStep("OwnedElement")])` + `LimitsSpec(null, 10000, 1)`.
      The 1ms timeout combined with repeat traversal should trigger timeout.
    - Assert: `response.isTruncated() == true`.
    - Assert: diagnostics contain at least one `EXECUTION_TRUNCATED` entry.
    - **Caveat**: Timing tests are inherently flaky. If the model is small enough to traverse in <1ms,
      increase the depth or add a `@RepeatedTest(3)` annotation with lenient assertion.
      Alternatively, accept that on fast machines the test may complete — assert that IF truncated,
      the diagnostic exists; IF not truncated, the result set is complete. This makes the test
      pass deterministically either way while still validating the invariant.

    ### 5. Repeat cycle diagnostic level

    **`repeat_cycleDiagnostic_isWarningLevel()`**
    - Setup: A→B→C→A cycle via Generalization links.
    - Query: `ProvidedSource(List.of(A))` + `RepeatStep(body=[TraverseStep("Generalization", null, Direction.FORWARD)])` + `LimitsSpec(12, 200, 5000)`.
    - Assert: diagnostics contain `CYCLE_DETECTED` with level `WARNING` (not ERROR).
    - Assert: response is NOT truncated (cycle detection terminates repeat, not the budget).

    **Private helpers:**
    - `createEngine()` → `new QueryEngine(this.session, List::of)`
    - `nameFilter(String name)` → returns a `FilterStep(CompareExpr(...))` for convenience.
