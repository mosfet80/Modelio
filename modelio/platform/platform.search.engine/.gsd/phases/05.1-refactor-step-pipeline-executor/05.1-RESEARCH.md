# Phase 5.1: Refactor StepPipelineExecutor — Research

**Researched:** 2026-02-24
**Domain:** Java refactoring — decomposition of a 618-line utility class
**Confidence:** HIGH (all findings verified against source code)

## Summary

`StepPipelineExecutor.java` is a 618-line static utility class that builds push-based pipelines of resolved query steps. It is the largest file in the executor package by a factor of 2.5× (next largest: `PreparedAsyncExecution` at 239 lines). The class has well-defined functional clusters: pipeline construction, step dispatching, BFS repeat logic, traverse logic (MDependency + LinkObject forward/backward), and path-extension helpers.

A code review produced 7 findings (3 IMPORTANT, 4 SUGGESTION). The triage below confirms 6 findings and rejects 1. The confirmed findings inform both an immediate refactoring plan for decomposition and a short list of correctness/documentation improvements.

**Primary recommendation:** Extract `StepPipelineExecutor` into 3 focused classes: `StepPipelineBuilder` (pipeline/chain construction), `RepeatStepExecutor` (BFS traversal), and `TraverseStepExecutor` (edge traversal + path helpers). Keep them package-private in the same executor package. This is a mechanical restructuring that should not change any public API or test code.

## Code Review Triage

### Finding 1: `emitAllDepths=false` silent empty result when body is entirely filtered by `globalVisited`

**Verdict: CONFIRMED — but severity is "documentation gap", not "bug"**

**Evidence:** In [StepPipelineExecutor.java](src/org/modelio/platform/query/internal/executor/StepPipelineExecutor.java#L380-L390), the natural-stop block is:

```java
if (nextFrontier.isEmpty()) {
    if (!repeat.emitAllDepths() && depth > 1) {
        for (NodeWithExplainOut item : frontier) {
            downstream.accept(item);
        }
    }
    break;
}
```

When `depth==1` and `nextFrontier` is empty (because the body produced nodes that were ALL already in `globalVisited`), the `depth > 1` guard prevents emission. This is **semantically correct** — the source node should not be emitted, and nothing was reachable beyond it — but no diagnostic is emitted to explain the empty result. A pipeline with two RepeatSteps sharing `globalVisited` can silently produce zero results for the second step's source.

This is not a bug: the contract is "emit deepest reachable frontier excluding source". When everything reachable is already visited, there is no frontier to emit. However, a diagnostic would improve observability.

**Action for refactoring phase:** Add an inline comment documenting this accepted behaviour in the extracted `RepeatStepExecutor`. Optionally emit a TRACE-level diagnostic. Do NOT change semantics.

### Finding 4: O(depth) list copying in `extendPathForDep` and `extendPathForLink`

**Verdict: CONFIRMED — but low practical impact**

**Evidence:** Both methods at [lines 598-618](src/org/modelio/platform/query/internal/executor/StepPipelineExecutor.java#L598-L618) perform:

```java
List<MObject> newNodes = new ArrayList<>(existing.nodes());   // copy N elements
newNodes.add(newNode);
List<PathStepOutput> newSteps = new ArrayList<>(existing.steps());  // copy N elements
newSteps.add(new MDependencyPathStepOutput(mc, dep));
return new PathOutput(List.copyOf(newNodes), List.copyOf(newSteps));  // copy N+1 again
```

This is indeed O(N) per hop → O(N²) total for a linear path of depth N, with two intermediate ArrayList allocations plus two `List.copyOf` final copies per hop.

**Practical impact:** For typical Modelio model depths (ownership trees rarely exceed 10–15 levels), the overhead is negligible. For deep traversals (e.g., large inheritance hierarchies up to depth 50+), total copies would be ~2500 elements — still modest. This is a **nice-to-fix** but should NOT block the refactoring.

**Action for refactoring phase:** Move helpers as-is into the extracted class. Optionally simplify the double-copy to a single-copy pattern (construct the target list directly at size N+1, no intermediate ArrayList) as a minor cleanup. Do NOT introduce a cons-list structure — it would change the `PathOutput` record type which is a public API type.

### Finding 5: `List.of(frontierItem)` allocated on every BFS body call

**Verdict: FALSE POSITIVE — immaterial**

**Evidence:** At [line 365](src/org/modelio/platform/query/internal/executor/StepPipelineExecutor.java#L365):

```java
final List<NodeWithExplainOut> bodyOutput =
        executeToList(repeat.body(), List.of(frontierItem), session);
```

`List.of(x)` returns a JDK internal `List12` (since Java 9) which is a fixed-size, zero-copy singleton list backed by a single field — it does NOT allocate an array. The JIT can further optimize it. Furthermore, within the same BFS body call, `executeToList` itself allocates a new `ArrayList` for `results` PLUS a new `HashSet` for `globalVisited` inside `buildChain`. The `List.of` allocation is dwarfed by these heavier allocations.

**The real allocation hotspot** is the `new HashSet<>()` inside `executeToList → buildChain` called on every frontier item — but even that is a design choice (body sub-pipeline isolation).

**Action for refactoring phase:** No action needed. This is not worth optimizing.

- **(d) Body entirely filtered by globalVisited**: NOT covered. No test sets up two consecutive RepeatSteps sharing globalVisited.

**Action for refactoring phase:** Add test coverage for scenarios (c) and (d) as part of refactoring validation. Scenarios (a) and (b) are lower priority but would be nice to have.

### Finding 7: `depth > 1` guard relies on undocumented invariant

**Verdict: CONFIRMED — trivial**

**Evidence:** At [line 383](src/org/modelio/platform/query/internal/executor/StepPipelineExecutor.java#L383):

```java
if (!repeat.emitAllDepths() && depth > 1) {
```

The invariant is that at `depth==1`, `frontier` contains exactly `[sourceItem]` (the initial seed). This is guaranteed by the initialization at line 356 (`frontier.add(sourceItem)`) and the fact that `frontier = nextFrontier` only happens at the bottom of the loop (line 399).

The existing comment at line 379 says `"Case c: natural stop"` and `"but not the initial source"`, which partially documents the intent but does not explain WHY `depth > 1` achieves source exclusion.

**Action for refactoring phase:** Add a one-line comment explaining the invariant in the extracted class. An assertion is overkill for a loop variable controlled 4 lines above.

## Decomposition Strategy

### Current structure (1 class, 618 lines)

`StepPipelineExecutor` contains 5 responsibility clusters:

| Cluster | Methods | Lines (est.) | Cohesion |
|---------|---------|-------------|----------|
| **Pipeline construction** | `buildPipeline`, `executeToList`, `buildChain`, `wrapStep` | ~130 | High — chain building + budget wiring |
| **Filter/Union wrapping** | `wrapFilter`, `wrapUnion` | ~30 | Low (simple delegates) |
| **Repeat/BFS** | `wrapRepeat` | ~100 | Self-contained BFS engine |
| **Traverse (edge navigation)** | `wrapTraverse`, `traverseMDependencyPush`, `traverseLinkObjectPush`, `traverseLinkForwardPush`, `traverseLinkBackwardPush`, `matchesStereotype`, `isValidElement` | ~200 | High — all edge traversal + filtering |
| **Path helpers** | `extendPathForDep`, `extendPathForLink` | ~25 | Used by Traverse only |

### Proposed decomposition (3 classes)

#### 1. `StepPipelineExecutor` (retained, slimmed)
- **Responsibility:** Pipeline construction, chain wiring, step dispatch, NOOP sink
- **Methods:** `buildPipeline`, `executeToList`, `buildChain`, `wrapStep`, `wrapFilter`, `wrapUnion`
- **Estimated size:** ~180 lines
- **Rationale:** `wrapFilter` and `wrapUnion` are thin enough (3 and 15 LOC respectively) to stay here rather than each getting their own class

#### 2. `RepeatStepExecutor` (new)
- **Responsibility:** BFS traversal, cycle detection, maxDepth, emitAllDepths, globalVisited
- **Methods:** `wrapRepeat` (refactored), possibly `processFrontierItem` extracted
- **Estimated size:** ~120 lines
- **Rationale:** The BFS logic is self-contained and the largest single method

#### 3. `TraverseStepExecutor` (new)
- **Responsibility:** MDependency and LinkObject edge traversal, path extension
- **Methods:** `wrapTraverse`, `traverseMDependencyPush`, `traverseLinkObjectPush`, `traverseLinkForwardPush`, `traverseLinkBackwardPush`, `matchesStereotype`, `isValidElement`, `extendPathForDep`, `extendPathForLink`
- **Estimated size:** ~250 lines
- **Rationale:** All traverse and path logic is tightly coupled (path helpers are only used by traverse methods)

### Visibility

All three classes remain **package-private** in `org.modelio.platform.query.internal.executor`. The only public entry point is `StepPipelineExecutor.buildPipeline()` (already the only public method).

`RepeatStepExecutor` and `TraverseStepExecutor` each expose a single package-private static method (`wrapRepeat` and `wrapTraverse` respectively) called from `StepPipelineExecutor.wrapStep`.

## Architecture Patterns

### Recommended approach: Mechanical Extract Class refactoring

This is a **pure structural refactoring** with no semantic changes:

1. **Create `RepeatStepExecutor.java`** — move `wrapRepeat` method as a package-private static method. It needs access to `executeToList` → call `StepPipelineExecutor.executeToList` (make it package-private instead of private).
2. **Create `TraverseStepExecutor.java`** — move all traverse and path methods.
3. **Update `wrapStep` in `StepPipelineExecutor`** — change case arms to delegate:
   ```java
   case TraverseStep t -> TraverseStepExecutor.wrapTraverse(t, downstream, session);
   case RepeatStep r -> RepeatStepExecutor.wrapRepeat(r, downstream, session, limits, globalVisited, diagnosticSink);
   ```
4. **Apply minor cleanups during extraction:**
   - Rename `mc` → `sourceClass` in `extendPathForDep`
   - Add invariant comment for `depth > 1` guard
   - Add accepted-behaviour comment for Finding 1

### Anti-patterns to avoid

- **Don't create interfaces for internal classes.** These are package-private static utilities — interfaces add ceremony without value.
- **Don't change method signatures.** Keep the same parameters, return types, and Consumer-based push model. The refactoring must be invisible to callers.
- **Don't merge with semantic changes.** Any behaviour changes (new diagnostics, test additions) should be separate tasks/commits from the structural extraction.

## Common Pitfalls

### Pitfall 1: Breaking `executeToList` visibility

`RepeatStepExecutor.wrapRepeat` calls `executeToList` to run the body sub-chain. Currently `executeToList` is `static` with default (package) visibility — but verify it's not `private`. If private, it must be relaxed to package-private.

**Evidence:** At line 181, `executeToList` is declared `static List<NodeWithExplainOut> executeToList(...)` — no access modifier, so it's already package-private. ✅ No change needed.

### Pitfall 2: Moving `NOOP_DIAGNOSTIC_SINK` reference

`executeToList` references `NOOP_DIAGNOSTIC_SINK` which is `static final` in `StepPipelineExecutor`. If `RepeatStepExecutor` calls `executeToList` on `StepPipelineExecutor`, this works transitively. But if `executeToList` is also moved, the reference breaks.

**Recommendation:** Keep `executeToList` in `StepPipelineExecutor` (it's part of pipeline construction). `RepeatStepExecutor.wrapRepeat` calls `StepPipelineExecutor.executeToList(...)`.

### Pitfall 3: Import bloat when splitting

Both new classes will need imports for `ResolvedStep.*`, `ResolvedEdge.*`, result types, etc. This is normal for a refactoring — don't let import lists discourage the split.

### Pitfall 4: `@objid` annotations

Per AGENTS.md: *"Do never modify, create or copy them. When in doubt, delete them."* When moving methods to new classes, **delete `@objid` annotations** from moved methods. Do NOT copy them to the new files. The new classes themselves should NOT have `@objid`.

## Open Questions

1. **Should `ExpressionEvaluator` and `isValidElement` be shared?** `TraverseStepExecutor` needs both. `ExpressionEvaluator` is already a separate class. `isValidElement` is a 1-line null/validity check — duplicating it in `TraverseStepExecutor` is acceptable, or it could become a tiny utility on `IQueryResponseFiller` or a small shared helper. Recommendation: keep it in `TraverseStepExecutor` since that's the only consumer.

2. **Should filter/union wrappers stay inlined?** `wrapFilter` is 3 LOC, `wrapUnion` is ~20 LOC. Moving them to their own classes would be over-engineering. Recommendation: keep in `StepPipelineExecutor`.
